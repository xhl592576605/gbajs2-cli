# 终端图片渲染可行性评估

本评估聚焦“图片级终端渲染”方案（Sixel、Kitty graphics 等），旨在判断其在 gbajs2-cli 中取代现有字符映射模式的可行性，覆盖兼容性、性能、架构影响与落地建议。

---

## 1. 背景与目标

- **痛点**：当前字符渲染模式在 `scale=1` 时，一个字符覆盖多像素，导致画面颗粒感强、对比度不稳定；`scale>1` 虽可提升细腻度，但终端尺寸需求急剧上升。
- **目标**：探索直接以位图方式输出 GBA 帧的方案，力争在终端内获得接近 GUI 的画质，同时保留 CLI 交互特性与兼容性。
- **范围**：仅评估基于终端图片协议（Sixel、Kitty graphics、iTerm2 inline image）的渲染；字体/Unicode 半图形方案另行讨论。

---

## 2. 评估假设与约束

| 维度 | 假设/约束 |
| --- | --- |
| 核心渲染 | GBA PPU 仍输出 240×160 RGBA 帧；允许在 Worker 或主线程对帧做色彩/缩放处理。 |
| 终端能力 | 不同平台终端能力差异大，必须先探测协议支持并提供 fallback（现有字符模式）。 |
| 依赖 | 优先纯 JS/Node 实现，尽量避免额外原生扩展；若必须，引入前需给出构建策略。 |
| 带宽 | 终端写入带宽受限，建议单帧 payload < 200 KB（压缩后）以保持 ≥ 30 FPS。 |
| 可维护性 | 渲染流水线需保留 diff/双缓冲思想，避免因图片模式回退时产生巨大结构性差异。 |

---

## 3. 方案矩阵

| 方案 | 协议描述 | 终端支持度 | 实现复杂度 | 性能预估 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| **Kitty graphics** | 通过 `ESC_Ga=T,f=100...ESC\` 发送像素块，可帧复用/分块；支持 zlib/base64 | Kitty、WezTerm（>=202207）、Ghostty（计划）、Contour | 中（需实现编码、缓存） | 高质量 24bit，帧尺寸≤200 KB | 希望在 Kitty/WezTerm 用户中解锁最高画质 |
| **Sixel** | DEC VT 系列位图协议，按 6 像素/列编码，支持 16/256 色并可模拟真彩 | XTerm (启用)、mlterm、mintty、WezTerm、Contour、yaft | 中偏高（需调色板 & dither） | 帧=~60 KB（Palette + Run-length），60 FPS 可期 | Linux/WSL/mintty 用户面广，适合作为首选图片模式 |
| **iTerm2 inline image** | `ESC]1337;File=...^G` 内嵌图片；支持 PNG/JPEG base64 | 仅 iTerm2 | 低（复用 PNG encoder） | 取决于 PNG 压缩，约 100~120 KB/帧 | 针对 iTerm2 用户的补充方案 |

结论：Sixel + Kitty 组合可覆盖 Linux/WSL/现代终端用户；iTerm2 协议可按需补充 macOS 用户。三者均需保留 fallback。

## 4. 平台兼容性与部署建议

| 平台 | 默认终端 | 支持 Sixel | 支持 Kitty | 是否需额外安装 |
| --- | --- | --- | --- | --- |
| macOS 13+ | Terminal.app | 否 | 否 | 用户需安装 Kitty/WezTerm 或 iTerm2 |
| macOS 13+ | iTerm2 | 否（官方未启用） | 否（自有协议） | 无需额外组件但需启用 inline image |
| Linux GNOME/KDE | GNOME Terminal / Konsole | 否（Konsole 计算中） | 否 | 建议安装 WezTerm、mlterm、XTerm（Sixel） |
| Linux 发行版 | WezTerm | 是（需 `wezterm enable-sixel`） | 是（默认） | 无 |
| Linux 发行版 | XTerm (>= 372) | 是（需 `--enable-sixel` 编译或包支持） | 否 | 若发行版包未开启则需自行编译 |
| Windows | Windows Terminal | 否 | 否 | 需安装 WezTerm/mintty/Contour |
| Windows (MSYS2/Cygwin) | mintty | 是 | 否 | 无 |

**部署策略**：文档中明确推荐“图片模式需要 Kitty/WezTerm/mintty/XTerm(含 Sixel)”等终端，可在 CLI 中检测到不支持时提示安装链接。

## 5. 渲染链路设计

```
GBA PPU (240×160 RGBA)
        │
        ▼
renderWorker
  1. 接收 RGBA Buffer + 帧序号
  2. 选择编码器（Sixel/Kitty/iTerm2)
  3. 生成压缩图块 + diff（可选）
        │
        ▼
主线程 GameCore
  4. 维护帧 cache（上一帧 ID、终端协议）
  5. 将编码后的 escape sequence 交给 TerminalViewport
        │
        ▼
TerminalViewport
  6. 控制光标 → 输出图片指令 → 恢复状态栏/输入提示
  7. 不支持时回落字符渲染
```

要点：沿用当前 Worker → 主线程消息通道，增加 `imagePayload` 类型；TerminalViewport 需要新增“图片层”概念以便在图片后继续绘制状态栏（可用 cursor save/restore）。

## 6. 关键技术点

1. **能力探测**
   - 读取 `process.env.TERM`, `TERM_PROGRAM`, `KITTY_WINDOW_ID`、`WEZTERM_EXECUTABLE` 等变量。
   - 通过发送极小图像并等待终端响应（Kitty 支持 query `ESC_Gi=1...`），作为最终确认。
2. **编码器实现**
   - Sixel：需构建最多 256 色调色板，可复用已有 npm 包（如 `sixel`）或在 Worker 中实现 Floyd-Steinberg 抖动。
   - Kitty：建议直接发送原始 RGB，按终端限制分片（如 4096 字节/片），可启用 zlib 压缩。
   - iTerm2：将 RGBA 转 PNG（使用 `pngjs`），base64 内嵌即可。
3. **内存与池化**
   - 保持帧缓冲复用，避免频繁 `Buffer.alloc`；对压缩结果使用 `BufferPool`。
   - Worker 返回 `transferList`，减少拷贝。
4. **状态栏叠加**
   - 图片模式下画面不再占用字符行，可在图片输出后额外渲染文本状态栏（以 cursor move + relative positioning 实现）。
5. **降级路径**
   - 探测失败或帧写入报错时自动切换到字符模式；
   - CLI 提供 `--image-render <kitty|sixel|auto|off>` 便于用户强制策略。

## 7. 性能与资源预估

| 指标 | Kitty (TrueColor) | Sixel (256 色) |
| --- | --- | --- |
| 单帧原始数据 | 240×160×3 ≈ 115 KB | 240×160 像素，经调色板压缩 ≈ 55 KB |
| 压缩方式 | zlib (可配级别) | 内建 run-length + palette |
| 预计带宽 (60 FPS) | ~6.9 MB/s，终端写入压力较大，建议 30 FPS | ~3.3 MB/s，可维持 45–60 FPS |
| CPU 开销 | zlib 压缩 + 分片复制 | 调色板生成 + Dither |
| Worker 耗时 | 3–5 ms/帧（Node 18+，单线程） | 4–7 ms/帧（含量化） |

**优化策略**：
- 允许帧率上限配置（30/45/60），在终端写入阻塞时自降帧率。
- 结合 diff 输出：当帧变化较小，可复用 Kitty ID 或 Sixel 滚动区域，仅更新局部块。
- 对静止帧启用帧缓存，避免重复写入。

## 8. 能力检测与回退流程

```
initRenderer(options)
  ▼
detectImageSupport()
  ├─ 检查 env (TERM, TERM_PROGRAM)
  ├─ 若命中 Kitty → 发 query ESC_Gi=31 并等待响应
  ├─ 若命中 WezTerm/mintty → 默认 Sixel，可发送一帧 1×1 试探
  └─ 均失败 → 标记 unsupported
  ▼
if supported
  setRenderer('image', protocol)
else
  fallback('ansi')
```

检测需设置超时（<200 ms），避免阻塞启动。若运行中检测失败（写入错误或终端 resize 后能力丢失）则回退并在 UI 提示“图片模式被禁用”。

## 10. 风险与缓解

| 风险 | 描述 | 缓解措施 |
| --- | --- | --- |
| 终端不支持 | 多数默认终端（macOS/Windows Terminal）不支持任一协议 | 文档+CLI 中提示推荐终端，自动回退到字符模式 |
| 性能不足 | 写入带宽导致帧率骤降 | 帧率限制+diff+帧缓存；提供 `--image-max-fps` |
| 颜色失真 | Sixel 256 色需抖动 | 自定义调色板、可配置 dither、允许 TrueColor Kitty 覆盖 |
| 状态栏覆盖 | 图片渲染占据整屏，状态栏可能被刷新 | 使用 cursor 保存/恢复，绘制顺序调整 |
| 实现复杂度 | Kitty/Sixel 编码器差异大 | 模块化 encoder 接口：`encode(frame, options) => { escape, metadata }` |

## 11. 测试策略

- **单元测试**：
  - `ImageEncoder` palette/dither 结果、Kitty 分片逻辑、能力检测 fallback。
- **集成测试**：
  - 使用 `node --test` 启动 mock 终端（借助 `pty.js`）验证 escape 序列；
  - 实机验证（Kitty、WezTerm、mintty）录制 GIF 作为凭证。
- **性能基准**：
  - `pnpm bench:image-render`，每帧统计编码耗时、payload 大小、终端 write 时延。
- **回归测试**：
  - 确保字符模式仍可启用、`--no-audio` 等选项不受影响。

---

## 12. 决策建议

1. **首选 Sixel + Kitty 双模式**：覆盖率最高，画质与性能兼顾，便于以 `auto` 方式自动选择。
2. **保持 ANSI/Braille 渲染作为安全网**：即便图片模式不可用也能继续游戏，避免阻断核心功能。
3. **迭代上线**：先实现 Sixel（Linux/WSL 用户受益最大），收集反馈后再扩展 Kitty/iTerm2。
4. **加强文档**：在 README/CLI 输出明确提示图片模式需要的终端，降低用户期望差。
